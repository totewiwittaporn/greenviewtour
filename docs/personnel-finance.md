# Personnel and finance workflows

Personnel records are separate from User profiles. `EMPLOYMENT` stores position and seasonal dates without compensation; `ATTENDANCE` records present, rest, paid leave, unpaid leave, absence or available without a job. No dispatch assignment creates an absence or salary deduction. Substitute staff are validated active and cannot substitute themselves.

The owner-approved payroll policy uses an explicit period, base wage and its reason/basis, then itemized additions and deductions with a reason for every line. Net payable is base wage plus additions minus deductions; an independent reviewer approves each period. Amounts use decimal strings and integer cents; no calendar divisor, automatic deduction, tax, social security or statutory leave formula is assumed. Trip allowances require a real Job Order staff assignment. Reimbursements require evidence references. Work advances and salary advances remain distinct from payroll and are not automatically deducted.

All records start as drafts. Only the author can edit, submit or cancel a draft, with a version check. A monetary beneficiary cannot approve their own request, record its payment or accept their own clearance; supplier-payment responsibility does not represent a personal beneficiary. Submit freezes the payload. A different authorized user approves or rejects. The author can revise a rejected record; revision clears prior approval and requires resubmission. Financial approval does not record payment; an authorized payer records an already completed external payment with its reference and date. No bank, email or LINE action occurs. A paid advance accepts itemized evidenced expenses/repayment plus returned cash totaling the exact advance, then a different reviewer accepts clearance. Rejected clearance returns to paid status for correction; the private command history retains prior submissions.

Supplier payments reference a received purchase order. Their amount, combined with other approved or paid requests, cannot exceed the order's receipted value. The shared transaction lock serializes approvals and avoids double reservation. A draft or rejected request does not reserve the balance. Paying does not mutate received stock or invent a supplier transfer.

Permissions are split by `personnel`, `payroll`, and `expenses` with separate view/edit/approve/pay duties. Personnel and Manager appointment authority do not imply payroll visibility. The API checks the current stored profile and permission overrides on every operation. API list responses expose minimal employee id/name references, and payroll remains outside the general User response. Private tables use RLS and revoke access from public application roles; the existing private backend connection performs authorized operations.

API: GET `/api/personnel-finance?kind=...&page=1` returns 25 records, server actions and minimal employee references. POST `/api/personnel-finance/save` accepts id/version/kind/title/employeeId/payload. POST `/api/personnel-finance/command` accepts a unique command id, recordId, version, action and action-specific evidence. The same command and actor replay the original response; a changed payload or actor with the same id conflicts. Current view and action permissions remain required on replay. Saves also record a deterministic namespaced id/version/actor fingerprint so uncertain create retries do not duplicate data or fail a successful identical save. All transitions increment revision and audit actor/action, without copying salary amounts into the general audit feed.

The UI reuses Core DataTable, Pagination, Dialog, Dropdown, SelectField, FormField and DateField. It retains failed edits, prevents duplicate submissions, protects dirty navigation and asks before discarding. View shows the persisted details and payment/clearance evidence; actions are supplied by the server. Conflicts instruct the editor to refresh rather than overwrite.

`seedPersonnelFinanceDemo` creates deterministic `DEMO FLOW` drafts for a preexisting employee whose name starts DEMO; it never overwrites a record, creates accounts, sets real salaries or sends payment. Root seed orchestration chooses the database and optional assigned Job Order. These are sample numbers for reviewing flow, not actual compensation.

Validation includes fixed-cent arithmetic, malformed dates, hidden salary input rejection, independent approval, blocked premature payments, stale edits, idempotency, clearance balancing and payroll view denial. Live migration/query and browser verification are performed by the integration task.

Remaining policy decisions: statutory payroll/tax rules and approved deduction calculations; external payroll/bank export; attachment upload/storage (current evidence is a reference); employee self-service payslips. These are not implied by recording drafts and externally completed payments.
